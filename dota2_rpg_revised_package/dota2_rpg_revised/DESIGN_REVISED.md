# 《Dota 2 RPG》（暂名）设计文档

> 类《圣兽之王》战术自动战斗 RPG · Dota 2 自定义地图

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v1.0 可实施修订版 |
| 修订日期 | 2026-09-05 |
| 平台 | Dota 2 游廊自定义游戏：Hammer + Lua + Panorama |
| 模式 | 单人 PVE、单局 Run、30 关线性闯关 |
| 持久化 | **不做跨局存档，不使用 LocalStorage；比赛结束即清空** |
| 战斗 | 战前编程，开战后全自动；玩家不能直接操作单位 |

---

## 0. 本次修订的硬性结论

本版不是在原文上继续堆功能，而是先删除不稳定、难平衡或与 Dota 2 实际能力冲突的设计，再重建可实施的核心。

| 原方案 | 本版结论 | 原因 |
| --- | --- | --- |
| 自定义物品直接依赖 Dota 默认商店 | **不作为正式方案**；使用自建 Panorama 商店 | 默认商店存在版本与专用服务器差异；即使 KV 能定义可购买物品，也不应把核心商店依赖在原生布局与排序上 |
| 物品全部塞入“12 格仓库小精灵” | 改为**服务端虚拟仓库 + 装备时生成真实物品** | 避免槽位、丢地、合成、复制、物品实体丢失等边界问题 |
| `IF 条件 THEN 动作 → 目标` | 改为**动作 → 目标硬条件 → 目标优先级 → 使用条件** | 更接近《圣兽之王》的阅读方式，也消除“存在符合目标”的伪条件 |
| 同一技能只能配置一条规则 | **允许同一技能重复配置多条规则** | 治疗、控制、位移技能必须能按不同紧急度和目标分别使用 |
| 条件支持 AND/OR 混合 | 单条规则只用 AND；OR 用两条规则表达 | 降低 UI、验证、调试和玩家理解成本 |
| 无规则时交给 Dota 默认 AI | 改为**显式兜底规则**，TacticEngine 全程拥有决策权 | 避免默认索敌打断玩家的规则、追击与施法 |
| 战斗提供 2x 和“跳过模拟” | 首发版只保证 1x；不承诺精确跳过 | Dota 原生技能、投射物、光环、触发器和随机过程无法由简化离线模型精确复现 |
| 招募品质直接赠送魔晶/神杖 | 从基础版本删除 | 不同英雄的魔晶/神杖价值差异极大，无法用统一品质倍率平衡 |
| 全拥有英雄平分经验池 | 上阵 100%、待命 50% 的**逐英雄固定经验** | 扩大英雄池不再反向惩罚主力成长，也不再需要经验卷轴补洞 |
| 经验卷轴商店 | 删除 | 原方案把成长曲线拆成“通关经验不足 + 必买卷轴”，增加操作但没有形成有趣选择 |
| LocalStorage、每日重置、存档迁移 | 全部删除 | 用户明确要求不做存档；本作按单局 Run 设计 |
| 固定写死英雄总数 | 使用构建时生成的兼容白名单 | Dota 英雄、技能和升级效果会随版本变化，文档不能写死数量 |
| 泛化的羁绊/词缀描述 | 补充数值预算、互斥规则、具体样例和代码接口 | 保证后期系统能接入现有战术引擎，而不是另起一套逻辑 |

## 1. 产品定位与核心循环

### 1.1 一句话定位

玩家组建 5 人队伍，为每名英雄配置类似《圣兽之王》的自动行动规则；战斗开始后不能微操，胜负主要由战前的阵容、装备、站位、目标条件和技能优先级决定。

### 1.2 核心体验

1. **规则可读**：玩家能在失败后明确看出“哪一条规则没有触发、目标为什么没选中、哪个技能被低优先级规则抢用了”。
2. **情报充分**：敌方英雄、等级、关键装备、词缀、阶段机制和主要战术在开战前可见。
3. **调整有效**：换目标条件、站位或装备后，战斗结果应该出现可解释的变化；敌人不读取玩家当前强度并动态追平。
4. **成长不过度稀释战术**：等级和装备提供容错，但不能让普攻档长期碾压战术关。

### 1.3 单局 Run 与无存档原则

- 每次创建比赛生成一个 `run_seed`，所有进度只存在当前服务端进程内。
- 30 关、金币、英雄、装备、羁绊、词缀结果和规则配置均不写入磁盘，也不写入 Panorama `LocalStorage`。
- 玩家断线后，只要同一场比赛仍在，可由服务端内存和 CustomNetTables 重建 UI；比赛结束、服务器关闭或重新建房后从零开始。
- 已通关关卡只在本次 Run 内锁定；开启新比赛后重新从第 1 关开始。
- 不设置每日重置、存档迁移、防改档或跨局遭遇种子。
- 开发者模式允许从章节预设开始，用于测试；正式模式不提供跳关。
- 因为没有跨局存档，完整 30 关 Run 的目标总时长为 **75~110 分钟，P90 不超过 120 分钟**；若引擎内测试长期超标，优先缩短战斗与准备流程，不用增加存档来掩盖节奏问题。
- 每 5 关进入一次当前比赛内的休整页，可暂停、查看队伍统计和重新配置，但它不是存档点；服务器结束后仍全部清空。

### 1.4 核心循环

```text
查看关卡情报
    ↓
调整 5 人编队、站位、装备与行动规则
    ↓
开始战斗，完全自动执行
    ↓
胜利：一次性金币、逐英雄经验、可能的装备掉落
失败：查看战斗日志，免费重新配置并重试
    ↓
进入下一关 / 重试当前关
```

### 1.5 失败与重试

- 当前关可无限重试，失败不扣金币、不减少永久次数。
- 第 3 次失败后，结算界面高亮本关的主要反制标签，但不自动改规则。
- 玩家可在战斗中点击“认输并重新布阵”；没有 2x、离线跳过或自动判胜。
- 这样可以避免无存档长 Run 因次数耗尽而直接报废，也让失败真正服务于战术学习。

## 2. Dota 2 自定义游戏能力边界

### 2.1 可直接使用的能力

| 功能 | 实现方式 | 结论 |
| --- | --- | --- |
| 地图、出生区、站位区、碰撞与屏障 | Hammer | 可做 |
| 服务端战斗逻辑 | Lua | 可做 |
| 自定义商店、规则编辑器、情报、日志 | Panorama XML/CSS/JS | 可做 |
| 客户端提交规则、购买、编队 | Custom Game Events | 可做，但服务端必须重新验证所有参数 |
| 服务端向 UI 同步当前 Run 状态 | CustomNetTables + Custom Game Events | 可做；大列表按英雄/规则拆 key，不发送单个巨型表 |
| 下达攻击、移动、施法命令 | `ExecuteOrderFromTable` | 可做 |
| 阻止玩家在战斗中直接控制英雄 | `SetExecuteOrderFilter` | 可做 |
| 查找单位、选择目标 | `FindUnitsInRadius`、缓存的战斗单位列表 | 可做 |
| 自定义 1~30 级经验曲线 | 自定义英雄等级与 XP 表 API | 可做 |
| 给英雄增加经验 | `AddExperience` | 可做 |
| 创建原版或自定义物品实体 | `CreateItem` | 可做 |
| 自定义 Buff、羁绊、词缀 | Lua modifier | 可做 |

### 2.2 有条件可做的能力

| 功能 | 风险 | 正式方案 |
| --- | --- | --- |
| 自定义物品出现在默认商店 | KV 层面存在商店标签和可购买配置，但原生商店布局、图标、排序与专用服务器行为可能随版本异常 | 自建 Panorama 商店；默认商店隐藏，不作为发布依赖 |
| 全英雄自动兼容 | 技能包含单位目标、点目标、无目标、切换、自动施法、向量、树木目标、子技能、变身和特殊资源 | 逐英雄/逐技能兼容白名单；未通过测试的不进入招募池 |
| 命石、先天技能与天赋 | 英雄生成变体、主动先天技能、天赋 UI 与 30 级全天赋行为不能按普通技能统一假定 | 首发每名英雄只开放一个专服验证变体，并为先天技能与天赋单独登记策略 |
| 原版主动装备自动进入规则系统 | 大部分可按行为标记适配，但部分装备有特殊双击、自身施放或目标类型 | 使用 item adapter；未适配装备只保留被动效果或从商店移除 |
| 魔晶/神杖 | 英雄间收益差距极大，且升级可能改变技能行为 | 只对验证通过的英雄开放为普通购买项；不再作为随机品质奖励 |
| 战斗重连恢复 UI | 当前服务端仍运行时可以从内存重建 | 只保证同一比赛内重连，不是存档 |

### 2.3 不作为首发承诺的能力

1. **精确 2x 战斗**：不依赖开发/作弊时间倍率；没有经过专用服务器验证前不加入正式 UI。
2. **精确“跳过战斗”**：不能用简化数学模型替代 Dota 引擎并声称结果一致。离线模拟器只用于平衡近似，玩家结算必须来自真实战斗。
3. **任何英雄、任何技能零配置自动工作**：复杂技能必须有 adapter 或明确标记为不支持。
4. **把默认 Dota 商店当作稳定的自定义商店容器**：即使某版本本地测试可用，也必须经过上传后的专用服务器回归测试。

## 3. 战斗与关卡结构

### 3.1 战斗状态机

```text
PREPARE → COUNTDOWN → FIGHT → SETTLE
```

- `PREPARE`：可编队、摆位、加点、购买、卖出、穿脱装备和编辑规则。
- `COUNTDOWN`：锁定阵容与装备，生成羁绊快照，应用本关词缀，清理所有旧锁定目标。
- `FIGHT`：关闭商店和物品操作；阻止玩家订单；TacticEngine 驱动所有战斗英雄。
- `SETTLE`：判定胜负、发一次性奖励、输出战斗日志。失败返回 `PREPARE`；胜利进入下一关。

### 3.2 阵容与站位

- 第 1~4 关最多上阵 3 人；进入第 5 关前开放 5 人编制，此后固定最多 5 人。
- 全部已招募英雄最多 10 人，未上阵英雄进入待命区。
- 准备阶段使用离散站位格，而不是完全自由移动：前排 3 格、后排 3 格，最多占 5 格。
- 站位格生成稳定标签：`front_row`、`back_row`、`left`、`center`、`right`。战斗开始后标签保持不变，不随走位改变。
- 目标条件里的“后排”“前排”读取站位快照，而不是按实时坐标猜测。

### 3.3 胜负与时间

- 胜利：敌方战斗单位全灭，或完成关卡明确写出的特殊目标。
- 失败：己方全灭、玩家认输、或超过 120 秒。
- Boss 阶段动画和不可选中演出不计入 120 秒；每段演出最多 3 秒。
- 召唤物不计入“必须击杀”的敌方英雄数，除非关卡配置明确标记 `must_kill = true`。

### 3.4 关卡结构

主线仍为 30 关：9 个野怪资源关，21 个英雄战术关。

| 关卡段 | 类型顺序 |
| --- | --- |
| 1~5 | 野 / 野 / 野 / 野 / 英 |
| 6~10 | 野 / 英 / 英 / 英 / 英 |
| 11~15 | 野 / 英 / 英 / 英 / 英 |
| 16~20 | 野 / 英 / 英 / 英 / 英 |
| 21~25 | 野 / 英 / 英 / 英 / 英 |
| 26~30 | 野 / 英 / 英 / 英 / 英 |

节点定位：

| 关卡 | 教学或检查主题 |
| --- | --- |
| 5 | 治疗者被前排保护：目标硬条件与后排优先 |
| 10 | Boss 引导技能：识别“引导中”并保留打断 |
| 15 | 刺客切后：保护后排、控制突进者、站位格 |
| 20 | 护盾与召唤物：驱散、换目标、区域条件 |
| 25 | 高恢复与濒死爆发：减疗、斩杀阈值、错开控制 |
| 30 | 三阶段规则组：阶段条件、爆发窗口与生存规则协同 |

### 3.5 关卡情报

战前必须显示：

- 敌方英雄或怪物、等级、站位标签、技能加点摘要。
- 每件装备的图标和名称；不隐藏关键主动装备。
- Boss/精英标签、羁绊或固定协同效果。
- 本关词缀的精确数值、触发条件和至少两种反制方向。
- 阶段切换阈值和有前摇的危险技能。
- 不直接展示敌方完整规则表，但展示可读摘要，例如“优先攻击后排”“低于 40% 时治疗最低血量友军”。

## 4. 英雄、招募与成长

### 4.1 英雄兼容白名单

- 不在文档中写死“当前共有多少英雄”。
- 构建脚本从当前版本英雄目录生成候选表，再读取 `hero_compatibility.kv` 决定正式招募池。
- 每名英雄必须通过：模型预缓存、出生、死亡、复活、命石/变体、先天技能、技能学习、天赋、施法类型、魔晶、神杖、主动装备和规则编辑器测试。
- 兼容状态分为：
  - `supported`：全部核心技能可自动执行。
  - `partial`：至少一个技能只能手写 adapter；未完成前商店注明限制。
  - `blocked`：不进入正式随机池。
- 不一次性预缓存全部英雄；按当前章节池和当前商店报价异步预缓存。

#### 命石、先天技能与天赋策略

- MVP **不向玩家开放命石选择**。每名英雄只采用 `hero_compatibility` 中登记并在上传后的专用服务器验证过的一个生成变体。
- 变体策略分为：`verified_default`（实际生成路径稳定得到的默认变体）、`verified_explicit`（项目已验证可显式指定的变体）、`blocked`（不能稳定生成，暂不开放）。不能仅因本地 Tools 模式可用就标记通过。
- 被动先天技能只进入属性与战斗日志，不生成动作；可主动施放的先天技能必须像普通技能一样登记 `cast_type`、目标阵营和 adapter。
- 玩家天赋在准备阶段选择；敌方英雄使用关卡配置里的固定 `talent_plan`。自动加点不得凭英雄等级猜测左右天赋。
- 30 级可能改变天赋生效范围；项目必须为每名开放到 30 级的英雄保存 `level_30_verified`。未验证时，终局基准不得使用该英雄。
- 兼容表至少保存：`variant_policy`、`variant_id`、`innate_policy`、`talent_plan_id`、`level_30_verified` 和 `dedicated_server_verified_patch`。

### 4.2 初始队伍

- 开局从经过验证的 12 名新手英雄中免费选择 3 名。
- 初始金币为 1000。
- 进入第 5 关前，通过招募商店补足至 5 人；设计上预留约 1800 金币完成两次同级招募。
- 新手池至少包含：2 名坦克、2 名近战输出、2 名远程输出、2 名治疗/护盾、2 名控制、2 名灵活位。

### 4.3 招募商店

| 当前关卡 | 报价等级 | 单名英雄基础价 |
| --- | ---: | ---: |
| 1~4 | 1 | 500 |
| 5~9 | 5 | 900 |
| 10~14 | 10 | 1600 |
| 15~19 | 15 | 2600 |
| 20~24 | 20 | 4000 |
| 25~30 | 24 | 5500 |

规则：

- 每次展示 5 名未拥有且已预缓存的兼容英雄。
- 每关第一次刷新免费，之后为 `100 / 200 / 300 / 400 / 500`，后续保持 500。
- 已拥有英雄不再出现；队伍上限 10 人。
- 不随机英雄品质，不赠送魔晶或神杖。
- 英雄报价显示：等级、定位标签、羁绊标签、当前兼容说明、可用主动技能数。
- 招募等级只解决追赶问题，不高于本章节玩家主力预期等级。

### 4.4 技能学习

- 英雄每升 1 级获得 1 技能点，准备阶段由玩家手动分配。
- 未学习的主动技能仍显示在规则编辑器中，但整条规则标记为“技能未学习”，战斗时直接跳过。
- 敌方英雄使用关卡配置中的固定技能加点，不按当前玩家动态改变。
- 技能加点、规则、装备都只保存在当前 Run 内存中。

### 4.5 删除旧品质系统

不再使用“精良 = 魔晶、史诗 = 神杖、传说 = 两者”的随机品质。原因：

- 不同英雄的升级收益无法放进统一价格倍率。
- 某些升级会改变技能目标类型、生成子技能或要求专用 UI，直接破坏自动适配。
- 后期已有羁绊和词缀，再叠加随机英雄品质会让平衡变量过多。

魔晶和神杖改为：

- 仅在兼容白名单中标记通过的英雄可以购买。
- 作为普通经济选择计入装备/升级预算。
- 购买后由服务端应用，规则编辑器刷新技能行为与 adapter。

## 5. 经验系统

### 5.1 自定义 1~30 级曲线

| 5 | 700 | 15 | 6700 | 25 | 22200 |

### 5.2 通关经验

经验不再是“全英雄平分一个池”，而是每名英雄按参与状态获得固定值：

- 上阵且在倒计时结束时属于主队：获得表中 100%。
- 待命英雄：获得表中 50%，向下取整。
- 战斗中阵亡不扣经验。

### 6.4 商店实现

- 正式 UI 使用 Panorama 自建商店；隐藏默认商店入口。
- 服务端维护物品白名单和价格；客户端只发送 `item_name`，不能发送价格、折扣或库存结果。
- 价格读取当前版本数据，例如 `GetItemCost(item_name)`；测试档案保存当时的 `economy_version` 和实际总价。
- 战斗中禁止购买、出售、穿脱、丢弃和合成。
- MVP 直接购买完整物品，不做原版配方树；配方系统稳定后再开放。
- 卖出返还实际买入价的 50%；掉落物按当前商店价的 50% 估值。

### 6.5 虚拟仓库

不再把所有库存依赖于一个实体单位的物品栏。

- 服务端 `RunState.warehouse[player_id]` 保存物品实例，而不是只保存物品名：`{ instance_id, item_name, purchase_cost, source, charges, custom_state }`，默认上限 60 项。
- 商店购买成功后先进入虚拟仓库，不在地图上生成物品实体。
- 点击“装备”时，服务端验证准备阶段、英雄归属和槽位后调用 `CreateItem`，把真实物品交给英雄。
- 点击“卸下”时，先读取层数、充能和项目自定义状态，再移除英雄物品实体并把同一 `instance_id` 返回虚拟仓库；不能把两个同名但状态不同的物品错误合并。
- 战斗中禁止穿脱，因此销毁并重建实体不会被用来刷新主动装备冷却。需要跨战斗保留充能或永久层数的物品，必须实现 `serialize_item_state` / `restore_item_state`。
- 关卡掉落直接进入虚拟仓库；仓库满时进入结算暂存区，玩家必须出售或腾出位置才能继续。
- UI 可按装备类型、价格、主动/被动、英雄适配标签筛选。
- 物品不会掉到地上，不允许信使、不允许地图商店距离判定，减少复制与拾取边界问题。

### 6.6 原版物品与自定义物品

- 优先使用经过验证的 Dota 原版装备。
- 自定义物品可以在 KV 和 Lua 中定义，但仍从自建商店购买。
- 主动装备进入战术规则前必须配置 `item_adapter`；没有 adapter 的主动装备不会出现在动作下拉框中。
- 中立物品、圣剑类掉落规则、消耗品、侦查物品和与普通 Dota 地图资源强绑定的物品默认禁用。
- 同名团队光环不允许在敌方配置中为了凑预算无意义叠加。

## 7. 行动逻辑系统：重做版

### 7.1 玩家看到的规则格式

规则不再显示为抽象的 `IF 条件 THEN 动作 → 目标`，而采用动作优先的自然语句：

```text
[优先级] 对 [目标阵营/类型]
使用 [动作]
仅限 [目标硬条件 1] 且 [目标硬条件 2]
优先 [目标优先级 1]，其次 [目标优先级 2]
当 [使用条件 1] 且 [使用条件 2]
接近策略：[仅限当前范围 / 允许接近]
```

UI 压缩显示示例：

```text
1. 治疗术 → 我方英雄
   仅限：生命 ≤ 40%
   优先：生命比例最低
   当：自身魔法 ≥ 25%
   仅限当前范围
```

### 7.2 删除“存在符合目标”条件

“存在符合目标的敌人/友军”不再作为玩家可选条件。原因：

- 目标是否存在本来就是目标解析的一部分。
- 玩家真正想表达的是“只打治疗者”“只打正在引导者”“只治疗低于 40% 的友军”。
- 当硬条件筛选后没有目标，该规则自然失败并继续检查下一条，不需要额外写一遍“存在”。

例如：

```text
旧：IF 存在正在施法的敌人 THEN 眩晕 → 正在施法的敌人
新：眩晕 → 敌方英雄；仅限：正在引导；优先：Boss；仅限当前范围
```

### 7.3 三类判断必须分开

#### A. 目标硬条件（Only / 仅限）

硬条件会删除不符合的候选目标。筛选后没有目标，则整条规则失败。

可用项：

- 生命百分比 `≤ / ≥ x%`
- 魔法百分比 `≤ / ≥ x%`
- 当前生命值 `≤ / ≥ x`
- 距离 `≤ x`
- 正在引导、正在施法前摇
- 被眩晕、被沉默、被缠绕、被减速、可驱散 Buff、可驱散 Debuff
- 具有显式标签：治疗者、Boss、精英、召唤者、前排、后排、近战、远程
- 是/不是英雄、召唤物、幻象
- 最近 N 秒受到过伤害
- 周围半径 R 内敌方/友方数量 `≥ N`
- 带有指定词缀、护盾或标记

#### B. 目标优先级（Prefer / 优先）

优先级只排序，不删除其他合法目标。没有首选目标时，仍可选次优目标。

可用项：

- 生命百分比最低/最高
- 当前生命最低/最高
- 距离最近/最远
- 护甲最低/最高
- 魔法抗性最低/最高
- 攻击力最高
- 优先治疗者、Boss、召唤者、后排、前排、正在引导者
- 优先被集火标记、带可驱散 Buff、带指定 Debuff
- 其次使用稳定 tie-break：离施法者更近，再按实体索引，保证同一状态下结果可复现

#### C. 使用条件（When / 当）

使用条件只读取施法者或全局战况，不承担选目标。

可用项：

- 自身生命/魔法百分比阈值
- 存活友军数、存活敌人数、已阵亡友军数
- 开战经过时间 `≥ / ≤ x 秒`
- 当前 Boss 阶段
- 自己最近 N 秒受到伤害
- 任意友军最近 N 秒受到伤害
- 本动作本场已使用次数 `< N`
- 本动作尚未使用过
- 自身没有指定 Buff / Debuff
- 当前没有近战敌人贴身
- 当前站位标签

技能是否已学习、是否冷却完毕、魔法是否足够、单位是否沉默等属于“动作可执行性”，由引擎自动检查，不要求玩家重复配置。

### 7.4 组合规则

- 每条规则最多 2 个目标硬条件、2 个目标优先级、2 个使用条件。
- 同一组内固定 AND，不提供 OR 下拉框。
- OR 通过两条规则表达，并由上下顺序决定优先级。
- 同一个技能或装备可以出现在多条规则中。
- 每名英雄固定提供 10 条可编辑规则 + 1 条系统兜底规则；不再根据技能/装备数量动态增删槽位。
- 玩家可禁用、复制、拖动排序和恢复模板。

例如同一个治疗技能可以写三次：

```text
1. 治疗术 → 我方英雄；仅限 HP≤25%；优先 HP%最低；允许接近
2. 治疗术 → 自身；仅限 HP≤45%；仅限当前范围
6. 治疗术 → 我方英雄；仅限 HP≤70%；优先 HP%最低；当敌人存活≤2；仅限当前范围
```

### 7.5 动作库

| 动作类别 | 说明 |
| --- | --- |
| 施放英雄技能 | 只显示已通过 adapter 校验的主动技能 |
| 使用主动装备 | 只显示当前已装备且通过 adapter 校验的物品 |
| 普通攻击 | 单位目标；可配置目标硬条件和优先级 |
| 移动到站位点 | 回到前排/后排格、靠近指定友军、远离最近敌人 |
| 保持距离 | 与选定目标维持最小/最大距离区间 |
| 待机 | 短时间不下达新订单；用于等待阶段或保留技能 |
| 切换技能状态 | 明确选择“开启”或“关闭”，而不是要求玩家另写“未开启”条件 |

### 7.6 技能目标类型与 adapter

所有动作先经过统一 adapter，不直接假定每个技能都是单位目标。

| 类型 | 通用处理 | 备注 |
| --- | --- | --- |
| 单位目标 | 选择一个合法单位并下达 cast-target | 支持友方、敌方、自身 |
| 点目标 | 选择最佳落点并下达 cast-position | 需要 AOE 半径和命中评分 |
| 无目标 | 检查自身周围命中数后 cast-no-target | 目标条件转为“范围内单位条件” |
| 切换 | 比较目标开关状态后切换一次 | 防止每 tick 反复开关 |
| 自动施法 | adapter 设置自动施法状态 | 必须避免与手动释放规则冲突 |
| 向量/双点目标 | 必须写英雄专用 adapter | 通用层不猜方向 |
| 树木、尸体、特殊实体目标 | 专用 adapter | 未适配前不进正式池 |
| 子技能/变身替换技能 | adapter 在状态变化时重建动作列表 | 规则引用稳定的逻辑动作 ID |

### 7.7 AOE 目标选择

点目标技能不能简单选择“血量最低敌人的脚下”。统一使用候选落点评分：

```text
score = 命中合法目标数 × 100
      + 命中首选标签数 × 30
      + 对低血量目标的权重
      - 命中应避开的友军数 × 200
      - 超出安全追击距离的惩罚
```

- 默认以每个候选单位当前位置作为一个落点，再加上敌群质心候选。
- 每 tick 复用空间查询结果，不为每条规则重复调用 `FindUnitsInRadius`。
- AOE 硬条件例：“半径内至少 3 名敌人”“至少命中 1 名正在引导的敌人”。
- AOE 优先级例：“优先命中后排最多”“优先总损失生命值最高的友军”。

### 7.8 范围与接近策略

不再使用容易永久卡住的“强制追击”命名。

| 模式 | 行为 |
| --- | --- |
| 仅限当前范围 | 只评估当前有效施法/攻击范围内的候选；没有目标则检查下一条规则 |
| 允许接近 | 可锁定全场候选并向其移动，但受最大追击距离与超时限制 |

默认限制：

- 技能接近超时 1.5 秒，普通攻击接近超时 2.5 秒。
- 超过初始锁定点 1200 距离或目标进入不可达区域时立即放弃。
- 目标死亡、无敌、隐身不可见、进入无效阵营、动作被移除或阶段切换时解除锁定。
- 紧急规则可以打断普通攻击追击，但不打断已进入施法前摇或正在引导的技能，除非 adapter 明确允许。

### 7.9 执行顺序

每个英雄每 0.2 秒检查一次，单位之间错开 tick：

1. 若死亡、被放逐或不在 `FIGHT`，跳过。
2. 若正在引导，保持当前动作。
3. 若正在施法前摇，除非动作已失效，否则不重复下单。
4. 处理仍有效的接近锁定。
5. 从第 1 条规则向下检查：
   - 动作存在且可执行；
   - 使用条件满足；
   - 取得动作允许的候选；
   - 应用目标硬条件；
   - 按目标优先级排序；
   - 生成单位或落点；
   - 下达一次订单并停止本 tick。
6. 若 10 条都失败，执行系统兜底：攻击当前范围内最近敌人；没有则向预设接敌点移动。

### 7.10 订单去重与玩家控制

- 同一单位、同一动作、同一目标在 0.25 秒内不重复下单。
- 战斗中所有来自玩家的移动、攻击、施法、物品和丢弃订单均由 order filter 拒绝。
- TacticEngine 下单时使用内部令牌绕过 filter。
- 准备阶段只允许移动到己方站位区、技能加点和装备操作。
- 不把默认 Dota AI 当兜底；系统兜底也是一条可审计的 TacticEngine 规则。

### 7.12 战斗日志与可解释性

每次规则检查不必全部刷屏，但关键状态必须可查询：

- 最近一次失败原因：冷却、魔法不足、使用条件失败、无合法目标、超出范围、adapter 不支持。
- 技能被更高优先级规则消耗后，在低优先级规则上显示“动作当前不可执行”。

- 开发者模式可开启逐 tick trace；正式 UI 默认只显示摘要。

## 8. 敌方英雄等级、装备与 AI

### 8.1 固定基准，不读取玩家实时强度

- 每关引用一个版本化 `benchmark_id`，包含标准玩家英雄、等级、技能、装备、站位、羁绊开关和规则模板。
- 敌方数据在发布前确定；运行时不读取玩家当前等级、金币、英雄或装备后加成。
- 玩家低配可以依靠更精准规则过关；玩家高配会获得更高容错，这是成长系统应有的效果。

### 8.2 21 个英雄关的建议表

### 8.3 敌方装备原则

- 装备必须服务于职责，而不是只按胜率榜凑高价。
- 坦克：先锋类、生存、团队魔抗/物抗、反伤；不同时堆满所有防御光环。
- 先手：跳刀/位移、控制补强、保命；必须在情报中展示。
- 物理输出：攻速/暴击/减甲/免控之间做取舍。
- 法术输出：施法距离、法强、回蓝、保命；不无限叠冷却缩减。
- 辅助：救援、驱散、团队鞋、位移；治疗者不能同时拥有全部最强救援件。
- 同名不可叠加光环不用于凑预算；无意义组件不计作“完整装备”。
- 敌方装备不会直接掉落；奖励只来自本关 `loot_table`。

### 8.4 敌方技能升级

- 每个关卡保存固定技能点表，不使用简单的“普通技能平均点、大招按等级自动学”作为最终配置。
- 技能点总数必须等于该英雄等级允许的点数。
- AI 用不到、adapter 未支持或会破坏关卡机制的技能可以不学，但情报界面必须真实显示。
- 魔晶/神杖只有在该英雄对应 adapter 验证通过后才能配置。

### 8.5 Boss 修正

Boss 强度不能只靠数倍生命：

| 节点 | Boss 修正建议 |
| --- | --- |
| 第 10 关 | +20% 最大生命，+5% 状态抗性，1 个有前摇的引导机制 |
| 第 20 关 | +35% 最大生命，+10% 状态抗性，2 阶段，召唤或护盾机制 |
| 第 30 关 | +60% 最大生命，+15% 状态抗性，3 阶段；每次阶段切换清锁定并重评规则 |

- Boss 不永久免疫控制。
- 单次不可规避伤害不超过基准后排英雄最大生命的 55%。
- 连续硬控必须留出至少 0.8 秒可行动窗口，除非玩家明确能在战前看到并反制。

### 8.6 野怪关锚点

| 关卡 | 敌方等级 | 数量 | 主要职责 |
| ---: | ---: | ---: | --- |
| 1 | 1 | 3 | 基础普攻教学 |
| 2 | 2 | 4 | 近战 + 远程 |
| 3 | 3 | 5 | 首个治疗怪 |
| 4 | 4~5 | 6 | 首个自爆/引导怪 |
| 6 | 6 | 6 | 资源回补，加入一名精英 |
| 11 | 11 | 7 | 治疗 + 控制 |
| 16 | 16 | 7 | 切后 + 反物理/反法术之一 |
| 21 | 21 | 8 | 至少三种职责协同 |
| 26 | 26 | 8 | 巨兽 + 支援 + 后排威胁 |

野怪的生命、攻击、护甲、魔抗与状态抗性由模板独立配置，并通过完整引擎战斗校准；不穿普通英雄装备。

### 8.7 胜率验收区间

| 关卡类型 | 默认模板胜率 | 针对规则胜率 | 获胜时长中位数 | P90 上限 |

## 9. 敌人 AI

### 9.1 与玩家共用规则语义

敌人和玩家使用同一套：

- 动作 adapter
- 目标硬条件
- 目标优先级
- 使用条件
- 接近策略
- AOE 评分
- 订单去重与追击锁定

敌方规则来自 `ai_profile`，玩家不能编辑，但战前可看到摘要。

### 9.2 AI Profile 示例

```lua
{
  id = "healer_protect_v1",
  rules = {
    {
      action = { kind = "ability", logical_id = "primary_heal" },
      target = { team = "ally", types = { "hero" } },
      target_filters = {
        { type = "hp_pct_lte", value = 0.35 }
      },
      target_priorities = {
        { type = "lowest_hp_pct" },
        { type = "prefer_tag", value = "boss" }
      },
      use_conditions = {
        { type = "self_mana_pct_gte", value = 0.20 }
      },
      approach = "range_only"
    }
  }
}
```

### 9.3 AI 难度来自哪里

- 低级敌人：2~4 条规则，只处理治疗、打断或普通攻击中的一项。
- 中期敌人：4~7 条规则，开始有同技能多情境规则和装备动作。
- 后期敌人：6~10 条规则，有阶段条件、保护后排、驱散与爆发窗口。
- 不通过缩短 0.2 秒 tick 或给予 AI 作弊视野提升难度。
- 隐身、战争迷雾和不可见单位是否启用由关卡规则明确决定；默认竞技场模式双方共享战斗可见性。

## 10. 羁绊系统

### 10.1 目标

羁绊为 5 人编队提供构筑方向，但不能：

- 自动选择目标或改写玩家规则顺序；
- 发放金币、经验、装备或免费刷新；
- 提供永久免控、无敌、复活循环或秒杀；
- 让某一组固定英雄成为唯一答案。

### 10.2 标签结构

- 每名英雄最多 2 个 `bond_tags`：通常 1 个战斗职责标签 + 1 个阵营/关系标签。
- 只统计倒计时结束时的 5 名上阵英雄。
- 召唤物、幻象、临时复制和待命英雄不计数。
- 同一英雄不会为同一个羁绊重复计数。
- 战斗开始时生成快照；死亡、复活和变身不重新计算。
- 阵容改变后在准备阶段实时预览，但不写入任何存档。

### 10.3 阈值与功率预算

- 常规羁绊使用 2/3 人阈值；少量主题羁绊可以使用 2/4。
- 达到高档时只生效高档，不与低档重复叠加。
- 2 人档目标等价于全队约 2.5%~3% 的有效战力。
- 3 人档目标等价于全队约 5%~6% 的有效战力。
- 同时激活多个羁绊后，综合收益上限约为标准队伍战力的 10%。
- 最大生命类羁绊总和上限 12%；伤害类上限 10%；冷却恢复上限 8%；移速上限 10%。
- 超出同一 `stacking_group` 上限时按比例压缩，而不是先到先得。

### 10.4 首批羁绊样例

| 羁绊 | 阈值 | 效果 | 设计边界 |
| --- | --- | --- | --- |
| 铁壁阵线 `frontline` | 2 | 该羁绊成员 +5% 最大生命 | 只强化成员 |
|  | 3 | 成员 +8% 最大生命；开战时后排获得其最大生命 5% 的护盾，持续 5 秒 | 护盾只触发一次 |
| 奥术共鸣 `caster` | 2 | 成员 +8% 魔法恢复 | 不直接减冷却 |
|  | 3 | 每名成员本场前 2 次成功施法后，为魔法比例最低友军恢复 3% 最大魔法；同单位 4 秒内最多触发一次 | 不改变技能目标 |
| 猎手协同 `hunter` | 2 | 首次普通攻击为目标施加 4 秒“猎物标记”；羁绊成员对其 +5% 伤害 | 每名施加者 10 秒冷却 |
|  | 3 | 标记增伤提高为 8% | 不自动集火，需玩家规则配合 |
| 救援网络 `support` | 2 | 成员造成的治疗与护盾 +6% | 不叠加到吸血 |
|  | 3 | 提高为 10%；本场第一次有友军低于 25% 时，为其提供最大生命 6% 护盾 | 每场一次 |
| 控制链 `controller` | 2 | 成员对正在被硬控的敌人 +4% 伤害 | 不延长控制时间 |
|  | 3 | 提高为 7% | 避免无限控制 |
| 召唤军势 `summoner` | 2 | 召唤物 +8% 最大生命、+8% 持续时间 | 不影响英雄本体 |
|  | 3 | 提高为 13% | 召唤物数量仍受技能原上限约束 |

### 10.5 关系羁绊

- 关系羁绊只为手工策划的双人或三人组合设置。
- 单个关系羁绊的收益不高于常规 2 人羁绊。
- 推荐使用一次性事件效果，例如“搭档首次低于 30% 时给小护盾”，而不是持续高额属性。
- 关系名单与具体数值放在 `bonds.kv`，不写进英雄代码。

### 10.6 UI

编队界面显示：

- 当前激活羁绊和档位；
- 每名英雄贡献的两个标签；
- 替换英雄后将新增/失去的羁绊；
- 叠加上限导致的实际生效数值；
- 战斗开始后的羁绊快照和触发日志。

### 10.7 数据结构

```lua
BONDS = {
  frontline = {
    name = "铁壁阵线",
    stacking_group = "max_health_pct",
    thresholds = {
      [2] = { member_max_health_pct = 5 },
      [3] = { member_max_health_pct = 8, opening_backline_shield_pct = 5 }
    }
  }
}
```

## 11. 敌方随机词缀系统

### 11.1 无存档条件下的生成

- 比赛创建时生成内存中的 `run_seed`。
- 每关使用 `Hash(run_seed, stage_id, affix_version)` 得到稳定的 `stage_seed`。
- 本关首次进入时生成词缀并缓存到 `RunState.stage_affixes[stage_id]`。
- 同一场比赛内失败重试不会重抽；结束比赛后没有任何持久化，下一 Run 会重新生成。
- 词缀生成不读取玩家英雄、装备、羁绊、规则或失败次数。

### 11.2 威胁预算

| 关卡范围 | 威胁点数 | 规则 |
| --- | ---: | --- |
| 1~4 | 0 | 新手阶段无词缀 |
| 5~9 | 1 | 1 个核心单位获得 1 个普通词缀 |
| 10~14 | 2 | 分给 1~2 个单位 |
| 15~19 | 3 | 普通单位最多 2 个词缀 |
| 20~24 | 4 | 优先领袖和职责单位，但至少覆盖 2 人 |
| 25~29 | 5 | 至少覆盖 3 个单位 |
| 30 | 6 | 最终 Boss 最多 3 个，其余点数至少分给 1 个其他单位 |

- 普通/稀有/史诗词缀消耗 1/2/3 点。
- 每关恰好使用预算；若白名单无法组成合法组合，则构建校验失败，不在运行时偷偷少用或多用。
- 普通单位最多 2 个，Boss 最多 3 个。
- 同名词缀、同一 `stacking_group` 或显式互斥词缀不能共存。
- 同一普通单位最多 1 个进攻类和 1 个防御/支援类词缀。

### 11.3 首批词缀样例

| 词缀 | 点数 | 精确效果 | 可表达的反制 |
| --- | ---: | --- | --- |
| 狂怒 | 1 | 生命低于 35% 时 +25 攻速、+10% 移速 | 在阈值前控制并爆发；低血量斩杀规则；减速/缴械 |
| 厚皮 | 1 | +12% 最大生命，受到的纯物理普通攻击伤害 -5% | 法术输出；减甲；先处理支援单位后再集火 |
| 破法外壳 | 1 | 本场第一次受到英雄技能伤害时，该次伤害 -40%，随后外壳失效 | 小技能破壳后爆发；多段伤害；换目标 |
| 护卫光环 | 2 | 600 范围友军 +4 护甲；光环持有者有明显图标 | 优先击杀持有者；魔法伤害；拉开阵型 |
| 净化脉冲 | 2 | 每 12 秒读条 0.7 秒，驱散 600 范围内 1 名友军的一个可驱散 Debuff | 打断读条；错开控制；先杀净化者 |
| 后排猎手 | 2 | 开战前 8 秒，其攻击类规则对后排目标增加高优先级；不绕过硬条件 | 后排保护；前后排换位；控制突进者 |
| 亡语鼓舞 | 2 | 死亡时使 500 范围友军 +15 攻速，持续 5 秒 | 拉开单位；延后击杀；范围控制 |
| 复苏核心 | 3 | 首次低于 20% 生命时读条 0.8 秒，恢复 15% 最大生命；可被打断，受减疗 | 减疗；打断；在读条前留爆发 |
| 受控反击 | 3 | 一次硬控结束后，获得 3 秒 +35% 状态抗性并在 0.5 秒前摇后造成小范围伤害；12 秒冷却 | 不重叠控制；远程拉扯；护盾/分散站位 |

### 11.4 禁止词缀

- 永久控制免疫或魔法免疫。
- 无前摇、无距离限制的秒杀。
- 永久隐身且没有可靠揭示手段。
- 无限刷新护盾或复活。
- 直接禁用玩家技能、删除规则、交换规则顺序或强制玩家锁定目标。
- 读取玩家阵容后生成的硬克制。
- 当前战术编辑器无法表达至少两种反制路径的效果。

### 11.5 与条件系统的联动

为保证词缀能被规则针对，目标硬条件/优先级必须支持：

- `has_affix = affix_id`
- `has_dispellable_buff`
- `is_channeling`
- `has_shield`
- `back_row / front_row`
- `hp_pct_lte`
- `nearby_allies_gte`

例如：

```text
驱散技能 → 敌方英雄；仅限 有可驱散Buff；优先 护卫光环持有者
眩晕 → 敌方英雄；仅限 正在引导；优先 净化脉冲/复苏核心
爆发技能 → 敌方英雄；仅限 HP≤22%；优先 带复苏核心
```

### 11.6 生成校验

发布前检查：

- 威胁点数是否正好用完；
- 单位标签是否满足白名单；
- 同名、互斥和 stacking group 是否冲突；
- 单位词缀数量、进攻/防御槽是否超限；
- 每个词缀是否声明至少 2 个 `counter_tags`；
- 对应目标条件/动作是否已在当前版本注册；
- 最高进攻组合、最高防御组合和高风险边界组合是否通过战斗批测。

### 12.2 RunState

当前比赛的唯一权威状态保存在服务端：

```lua
RunState = {
  run_seed = 0,
  stage = 1,
  phase = "PREPARE",
  gold = {},
  roster = {},
  active_lineup = {},
  warehouse = {},
  rules = {},
  stage_affixes = {},
  claimed_rewards = {}
}
```

- Panorama 不是权威数据源。
- 客户端断线重连时请求 `rpg_request_full_state`，服务端重新推送当前阶段、金币、英雄、仓库和分片规则。
- 不读取或写入 LocalStorage。
- `claimed_rewards` 只防止当前服务端会话内重复结算。

### 12.3 网络同步

- CustomNetTables 保存频繁读取的小状态：阶段、金币、当前英雄摘要、战斗状态。单个 key 更新存在 16,384 字节上限，工程安全目标设为不超过 12 KB。
- 每名英雄、每条规则使用独立 key，例如 `hero_3`、`rules_3_page_1`，避免一个巨型嵌套对象。
- 规则编辑、购买、装备和编队通过 Custom Game Events 提交。
- 服务端校验：玩家 ID、阶段、英雄归属、动作是否存在、参数范围、目标条件兼容、金币与仓库容量。
- 服务端返回规范化后的规则；客户端不能假设提交即成功。
- 高频日志和完整规则编辑结果优先用定向 Custom Game Event 增量推送；NetTable key 的任意字段变化都会重发该 key，因此不要把整场 Run 状态塞进一个 key。

### 12.4 性能

战场通常为 5 对 3~7 个英雄，加少量召唤物。每 0.2 秒执行：

- 每个单位只构建一次可见友军/敌军候选缓存。
- 规则条件编译成函数或枚举分派，不在 tick 中解析字符串。
- 只在 dirty 时重建技能与装备 action 列表。
- 近期受击、施法、死亡和阶段事件通过环形缓冲记录，不遍历完整日志。
- 点目标 AOE 共用空间索引；禁止每条规则多次全图 `FindUnitsInRadius`。
- 订单有 0.25 秒签名去重。

### 12.5 数据验证

构建失败条件：

- 30 关类型数不是 9 野怪 + 21 英雄。
- 英雄关人数与章节规则不符。
- 敌方等级、技能点、装备价值或 Boss modifier 越界。
- `benchmark_id`、`ai_profile`、`adapter_id`、`bond_tag`、`affix_id` 引用不存在。
- 主动技能或装备进入招募/商店白名单，但没有可用 adapter。
- 英雄缺少已验证的命石/变体策略、主动先天技能 adapter、敌方天赋计划或 30 级验证结果。
- 词缀没有两种反制标签或产生非法组合。
- 金币/XP 改动后，相关 benchmark 未重新跑批测。

## 13. 平衡与测试工具

### 13.1 不做“完全离线复刻 Dota”

Dota 的投射物、攻击前摇、转身、光环、modifier 顺序、技能内部脚本和物理碰撞无法在一个简化 Lua 数学模型中完全复刻。因此测试分两层：

1. **纯逻辑测试**：条件筛选、目标排序、规则优先级、随机词缀生成、金币/XP 校验，可在无 Dota 实体的环境运行。
2. **引擎内批量战斗**：真正创建单位、技能和装备，在 Dota 引擎内以固定种子重复战斗，作为最终平衡依据。

### 13.2 批测规模

- 每次提交：关键关卡 50 个固定种子冒烟测试。
- 每个章节完成：对应 5 关 × 200 个固定种子。
- 发布候选：30 关 × 关键阵容/规则档 × 500 个固定种子。
- 词缀阶段额外测试：无词缀、期望组合、最高进攻、最高防御、高风险互斥边界。
- 羁绊阶段额外测试：无羁绊、常见双羁绊、最大合法羁绊。
- 完整 Run 节奏测试至少记录 30 个真人或回放样本；总时长中位数目标 75~110 分钟，P90 不超过 120 分钟，单关准备阶段 P90 不超过 150 秒。

### 13.3 标准玩家档案

至少覆盖：

- 均衡队、物理爆发、法术爆发、持续恢复、切后、低控制。
- 70% 目标装备价值 + 针对规则。
- 100% 目标装备价值 + 默认模板。
- 100% 目标装备价值 + 针对规则。
- 只有兜底普攻规则。
- 羁绊关闭、期望羁绊、最大合法羁绊。

每个档案必须保存具体英雄、等级、技能点、每格装备、站位和完整规则，不允许只写“平均等级 + 总装备价”。

### 13.4 输出指标

- 胜率、获胜时间中位数、P90。
- 每名英雄存活率、输出、承伤、治疗、控制时长。
- 每条规则成功次数、无目标次数、动作不可执行次数、接近超时次数。
- 关键技能首次释放时间和被打断次数。
- 敌我实际装备总价和魔晶/神杖清单。
- 英雄命石/变体、先天技能、天赋计划与 30 级验证标记。
- 羁绊实际生效数值和词缀触发次数。

## 16. Demo 代码说明

随本文档提供的 `demo/` 包含：

- `tactics/condition_registry.lua`：使用条件与目标硬条件注册表。
- `tactics/target_selector.lua`：硬筛选、软优先级、稳定排序和 AOE 落点。
- `tactics/action_adapter.lua`：攻击、单位目标、点目标、无目标和切换技能下单。
- `tactics/tactic_engine.lua`：0.2 秒规则循环、重复动作、追击与兜底。
- `tactics/order_filter.lua`：战斗中拒绝玩家订单、允许引擎内部订单。
- `progression/progression.lua`：30 级 XP 表和 1~29 关奖励。
- `shop/shop_service.lua`：服务端权威价格、虚拟仓库、装备/卸下流程。
- `bonds/bond_system.lua`：羁绊计数、阈值快照和 modifier 参数下发。
- `affixes/affix_system.lua`：内存种子、威胁点数、互斥与稳定生成。
- Panorama 示例：新战术规则的 UI 数据结构和自建商店事件。

代码是可整合的工程骨架，不是完整成品地图。接入前仍需：

- 在 `addon_game_mode.lua` 中 `require`、注册 modifier、初始化各服务；
- 把你当前 BattleManager 的英雄列表、阶段和数据表接口接入；
- 为正式招募池逐个补齐特殊技能 adapter；
- 在本地工具和上传后的专用服务器各跑一次回归测试。

## 17. 技术依据与版本注意

本设计依赖的 Dota 2 Workshop 能力包括 Hammer、Lua、Panorama、Custom Game Events、CustomNetTables、订单 API、订单过滤器、自定义英雄等级/XP、物品创建和 Lua modifier。正式发布前应以当时的 Valve 文档和上传后的专用服务器实测为准。命石/英雄变体接口在不同创建路径中的可用性也必须单独回归，不能沿用普通技能兼容结论。

默认商店的结论需要特别保守：KV 定义层面存在自定义物品的价格、可购买状态和商店标签，但 2026 年 7.41e 后已有公开问题报告指出，`scripts/shops.txt`、物品隐藏、排序、图标和点击行为在本地与专用服务器之间可能不一致。因此本项目把自建 Panorama 商店定为唯一正式入口。
